# דף הכרעות לשגיב — ניהול עסקה דינמי

תאריך: 2026-09-14  
מטרה: לסגור את J1 ואת החלק המסחרי של J2 בלי שהמהנדס ימציא כלל מסחר.

מקור: `DYNAMIC_MANAGEMENT_TREE_HE.html`, `MANAGEMENT_DIAGRAMS_HE.html`,
`ACCOUNT_1000_MANAGEMENT_REPORT_HE.html`, התמלול, ותוכנית האב בסעיף 10א.
המסמך אינו מאשר ערכי הדגמה שב־HTML, אינו מפעיל ברוקר ואינו מחליף את
`fixed_full_tp1_v1` כזרוע הביקורת הראשונה.

## איך ממלאים

לכל הכרעה יש לרשום:

1. תשובה מחייבת אחת, כולל ערכים/יחידות/טווחי זמן אם ישנם.
2. אילו inputs מהעץ נדרשים ומהו זמן הזמינות שלהם (`as_of`).
3. פעולה מותרת, שינוי הכמות/הסטופ/הפקודה, וסיבת רישום.
4. דוגמה חיובית ודוגמה נגדית מאותו סוג עסקה.
5. מה קורה כשהמידע חסר, סותר או מאוחר.

תשובה כגון “תלוי בגרף” היא תקפה רק אם מצורפת לרשימת תנאים מדידה או אם
מסומנת במפורש כ־`HUMAN_ONLY`; היא אינה כלל אוטומטי ולא label לאימון.

## 1. מצב התזה

| מצב | הגדרה שגיב צריך לאשר | inputs ועיתוי | פעולה מותרת | fallback בחוסר מידע |
| --- | --- | --- | --- | --- |
| `HELD` | מה מוכיח שהתזה עדיין תקפה? | | | |
| `WEAKENING` | מהו סימן מוקדם שאינו שבירה? | | | |
| `BROKEN` | מהו תנאי יציאה מחייב לפני הסטופ? | | | |
| `UNVERIFIED` | איזה מידע חסר או סותר? | | | |
| `RECOVERED` | מתי ראיה חדשה מתקנת weakening? | | | |

נדרש להבחין בין תוצאת נר סגור, quote רגעי, order-flow, חדשות וראיה ידנית.
אין להפוך “לא ידוע” ל־`BROKEN` או ל־`HELD` ללא כלל מפורש.

## 2. סדר פעולות כאשר יותר מדבר אחד נכון

העץ מציב `REALLOCATE` (M10) לפני `MODIFY_STOP` (M11), אך ההסבר דורש הגנה
לפני שינוי חשיפה. יש לאשר scheduler יחיד, לכל event loop:

| קדימות | אירוע | החלטה/פעולה | מה נשאר בתוקף עד ACK | כשל/timeout |
| --- | --- | --- | --- | --- |
| 1 | reconciliation, fill לא מזוהה או סתירה | | | |
| 2 | חוסר הגנה על כמות בפועל | | | |
| 3 | kill switch / breach | | | |
| 4 | `BROKEN` או יציאת זמן/חדשות מחייבת | | | |
| 5 | שינוי סטופ / BE / trailing | | | |
| 6 | partial / reallocation / add | | | |
| 7 | `HOLD` | | | |

הפעולה חייבת להיות idempotent: אותה ראיה לא יכולה ליצור partial, stop-modify
או add פעמיים.

## 3. כניסה בתוך zone והוספה

| נושא | הכרעה נדרשת |
| --- | --- |
| כניסה ב־zone | האם הכניסה היא בתחילת/אמצע/סוף הטווח, או לפי quote/feature אחר? האם Long ו־Short שונים? |
| expiry | כמה זמן intent ממתין לפני ביטול, לפי פרופיל? |
| fill חלקי | האם להגן מיד על הכמות שמולאה, לבטל יתרה, או להמתין? |
| re-entry | מתי הוא מותר, כמה פעמים ב־episode, והאם הוא אותו thesis או thesis חדש? |
| add / ladder | תנאי break מאומת, כמות, תקציב סיכון שנותר, ואיסור מפורש על averaging down. |
| invalidation בזמן pending | ביטול, מצב כמות שמולאה, ואופן reconciliation. |

כל הוספה מחייבת תשובה לגבי כמות, סטופ תקף לכמות החדשה, OCO/פקודות יעד,
תקציב episode וחשיפת portfolio. “המחיר חזר” לבדו אינו טריגר מספק.

## 4. partials, targets ו־runner

ב־HTML קיימים פרופילים ודוגמאות: תגובה קצרה, מאוזן, המשכיות ומהפך. אלה
דוגמאות עיצוביות עד ששגיב מאשר אותן. עבור כל פרופיל יש למלא:

| פרופיל | תנאי בחירה | intended legs | effective legs לאחר lot-step | TP1/TP2/TP3/runner | מתי סוגרים מוקדם? |
| --- | --- | --- | --- | --- | --- |
| תגובה קצרה / סקאלפ | | | | | |
| מאוזן | | | | | |
| המשכיות / הרחבה | | | | | |
| מהפך מתפתח | | | | | |

לא משנים allocation של רגל שכבר מומשה. אם rounding או מינימום lot משנים
את החלוקה, נרשמים גם `intended_legs` וגם `effective_legs`.

## 7. חשבון קטן, sizing ומפרט ברוקר

דוח ה־$1,000 מתאר תרחישים אך אינו מפרט ברוקר מאומת. נדרשות ההכרעות:

- האם פרופיל חשבון קטן משנה רק `effective_legs`, או גם תנאי כניסה/יציאה?
- מהו מקור אמת ל־tick value, contract size, lot step/min/max, margin,
  stop/freeze level, spread, commission, slippage ו־swap?
- מהו הסיכון המרבי ל־trade, episode, cluster, יום ושבוע; ומה הפעולה בעת חריגה?
- מהו כלל ההקצאה אם הכמות החוקית קטנה מהחלוקה המתוכננת?

עד שאומת מפרט ברוקר, פעולה במצב כזה היא `SHADOW_ONLY`, לא מדיניות ביצוע.

## 8. דוגמאות קבלה מינימליות

שגיב יספק לכל אחת דוגמה אמיתית או replayable עם זמני נתונים:

1. `HELD` אחרי TP1 ללא BE, ולאחר מכן המשך ליעד הבא.
2. `WEAKENING` שמוביל ל־partial/הגנה אך לא ליציאה מלאה.
3. `BROKEN` שמוביל ליציאה מוקדמת לפני סטופ.
4. `UNVERIFIED` שבו חסר order-flow/חדשות והפעולה השמרנית ידועה.
5. fill חלקי ואז שינוי או ביטול יתרת הכניסה.
6. add חוקי לאחר break, עם תקציב והגנה על הכמות הנוספת.
7. מרוץ cancel מול fill ו־reconciliation.
8. אותה תזה בחשבון קטן שבו lot rounding משנה את הרגליים.

לכל דוגמה: snapshot לפני הפעולה, פעולה שנבחרה, פעולות חוקיות שלא נבחרו,
מצב לאחר הפעולה, והסיבה. זו יחידת האימון העתידית — לא רק WIN/LOSS סופי.

## Definition of Done ל־J1/J2

J1/J2 אינם סגורים עד שכל שורה רלוונטית לעיל כוללת החלטה או `HUMAN_ONLY`,
דוגמאות מנוגדות, מקור נתונים ועיתוי, fallback, והשפעה מפורשת על מצב/כמות/
פקודות. לאחר מכן נוכל לקבע קטלוג policy ולכתוב את J3 בלי לנחש את המסחר.
